🔴 1. Critical Bugs

C-01
Data Disappears on Page Refresh — Root Cause Confirmed
critical

File: src/repositories/baseRepo.ts — mirrorLocalList() method

This is the exact bug causing data loss on refresh. The flow:

// BaseRepo.create() — SILENT FAILURE PATH
async create(input) {
  const entity = { ...build entity... };
  if (this.canRemote()) {
    try {
      const created = await cloudRepoCreate(...); // ← calls /api/cloud/entity.php
      await this.mirrorLocal(created);            // saved to cloud + IndexedDB ✅
      return created;
    } catch {
      // SWALLOWED — no user feedback, no retry
    }
  }
  await this.table().add(entity);  // fallback: IndexedDB only
  return entity;                   // ← data visible NOW but NOT in cloud
}

// On refresh: BaseRepo.list() runs mirrorLocalList()
private async mirrorLocalList(userId, rows) {
  const local = await this.table().where("userId").equals(userId).toArray();
  const remoteIds = new Set(rows.map(r => r.id));  // ← empty if cloud had no data
  const toDelete = local.filter(l => !remoteIds.has(l.id)).map(l => l.id);
  if (toDelete.length > 0) await this.table().bulkDelete(toDelete); // ← WIPES LOCAL DATA
}

When does cloudRepoCreate fail? Network timeout, API returning a PHP error page (non-JSON response), DB connection blip, or the JWT being expired/invalid at the moment of first save. The catch block swallows it silently — user sees data, but it only exists in IndexedDB. On refresh, list() gets empty from cloud and mirrorLocalList destroys IndexedDB records.

✅ Fix — Two parts required

Part 1: In mirrorLocalList(), never delete local records if the remote array is empty AND local has records for that user. An empty response from cloud is suspicious — it might mean an API error slipped past the catch. At minimum, guard with if (rows.length === 0 && local.length > 0) return;.

Part 2: In create(), don't silently swallow cloud failures. If the cloud write fails, either (a) mark the entity with a pendingSync: true flag and show a "saved locally, will sync" toast, or (b) throw the error to the caller so the form can inform the user. Silent fallback is the enemy here.

// Part 1 — Safe mirrorLocalList
private async mirrorLocalList(userId: ID, rows: T[]) {
  const local = await this.table().where("userId").equals(userId).toArray();
  if (rows.length === 0 && local.length > 0) return; // don't wipe if cloud empty
  const remoteIds = new Set(rows.map((r) => r.id));
  const toDelete = local.filter((l) => !remoteIds.has(l.id)).map((l) => l.id);
  if (toDelete.length > 0) await this.table().bulkDelete(toDelete);
  if (rows.length > 0) await this.table().bulkPut(rows);
}

// Part 2 — Explicit failure toast in create()
if (this.canRemote()) {
  try {
    const created = await cloudRepoCreate(...);
    await this.mirrorLocal(created);
    return created;
  } catch (e) {
    // Fallback to local but warn user
    console.warn(`Cloud write failed for ${this.cloudCollection}:`, e);
    // optionally: useUIStore.getState().toast({ title: "Saved locally, sync pending", kind: "warning" });
  }
}
await this.table().add(entity);
return entity;
C-02
Auth Hydration Fails When IndexedDB Is Cleared — User Locked Out Despite Valid JWT
critical

File: src/store/authStore.ts — hydrate()

On refresh, hydrate() reads the user from IndexedDB using userRepo.get(session.userId). If IndexedDB is cleared (browser data clear, incognito, device change), this returns null and the user is forced back to login — even though their JWT token is perfectly valid.

hydrate: async () => {
  const session = getLocalSession();           // sv:session (localStorage) ✅
  const cloudToken = localStorage.getItem(CLOUD_TOKEN_KEY);  // sv:cloud_token ✅
  if (session && cloudToken) {
    current = (await userRepo.get(session.userId)) ?? null; // IndexedDB — can be empty!
    // If null → currentUser = null → login screen shown, all data appears gone
  }
}
✅ Fix — Fallback to /api/cloud/me.php

If IndexedDB returns null, call the cloud /api/cloud/me.php endpoint (which is already implemented) to re-hydrate the user identity, then reconstruct the local user record via ensureLocalMirrorProfile().

if (session && cloudToken) {
  current = (await userRepo.get(session.userId)) ?? null;
  if (!current) {
      // IndexedDB cleared — re-hydrate from cloud
      try {
        const me = await cloudMe(); // calls /api/cloud/me.php
        // re-create local mirror without PIN — user needs to re-enter PIN
        // OR redirect to cloud sign-in with username pre-filled
      } catch { /* token invalid, show login */ }
    }
}

🟠 2. High Priority Issues

H-01
JWT Secret Is the Literal Placeholder — Security Risk
high

File: .env

CLOUD_JWT_SECRET="replace-with-a-strong-long-random-secret"

This is the exact text from .env.example being used as the actual JWT signing secret. Any attacker who reads the source code (e.g., if the repo is public or if they see the .env.example) can forge valid JWTs for any user.

✅ Fix

Generate a real secret: openssl rand -hex 48 and replace it in .env on the server. Never commit real secrets to the repo.

H-02
APP_ENV Is "development" on Hosting — Wrong CORS + Loose Behavior
high

File: .env — APP_ENV="development"

When APP_ENV=development, the CORS security applies Access-Control-Allow-Origin: * (any domain can call your API) instead of the locked-down production behavior. Also, CORS_ALLOWED_ORIGINS is set to localhost addresses which won't match darvikstore.info at all.

✅ Fix on Hosting Server

In .env on the host: set APP_ENV="production" and update CORS_ALLOWED_ORIGINS="https://darvikstore.info"

H-04
Plan Creation Form Is Incomplete — Only Name Field, Price/Interval Hardcoded

The "Create Plan" form only has a name input. It hardcodes price_inr: "499.00", billing_interval: "monthly", and trial_days: 7. The backend admin_plans_upsert() validates all fields so partial data will fail validation on the server.

H-05
Rate Limiting Uses File-Based JSON — Race Condition Under Load
high

File: php/helpers/security.php — rate_limit_guard()

Rate limiting reads/writes a JSON file (data/rate_limits.json) on every API request. Under concurrent traffic, two requests can read the same file simultaneously, both see count=1, both write count=2 — the limit is never enforced correctly. This is also slow (file I/O on every request).

✅ Fix

Store rate limit counters in MySQL using the existing DB connection. A single INSERT ... ON DUPLICATE KEY UPDATE attempt_count = attempt_count + 1 is atomic. Alternatively, use Redis/APCu if available on your host.

medium

Change kind: "danger" → kind: "error" in both places in UserManagementPage.tsx.

M-04
No loadAll() Trigger After Cloud Pull — UI Doesn't Reflect New Data
medium

File: src/components/pages/SettingsPage.tsx — handleCloudPull()

After pulling cloud data, records are merged into local state with upsertLocal(). However, loadAll(user) is never called, so some derived views (dashboard balances, category counts) won't reflect the newly pulled data until the user navigates away and back.

✅ Fix

After handleCloudPull completes, call await loadAll(user) (same as done in handleCloudLogin in the same file).

M-05
Schema Mismatch — schema.sql References Old cloud_users Table
medium

File: sql/schema.sql

The original schema.sql still creates a cloud_users table with a foreign key to it in cloud_collection_rows. The newer 20260427_all_in_one.sql correctly migrates to a unified users table. If someone installs using the old schema.sql, data will be stored in the wrong table and all API calls will fail.

✅ Fix

Update schema.sql to match 20260427_all_in_one.sql exactly, or delete schema.sql and update the setup guide to use 20260427_all_in_one.sql as the canonical install file.

M-06
No Loading or Error State in Admin Pages — Blank Screen on API Failure
medium

Files: All 5 admin pages

Most admin pages call APIs in useEffect and silently set state to [] or {} on error. There's no spinner while loading, no error banner if the API fails, and no empty state UI. Users will see a blank white page with no indication of what happened.

✅ Fix

Add loading and error state to each admin page. Show a spinner while fetching, and show an error card with a "Retry" button on failure. The pattern is already done in UserManagementPage (partially) — extend it to all pages.

☁️ 6. Phase 2 Cloud Sync — Decision Required

DECISION
The "Phase 2 Cloud Sync" section in Settings doesn't make sense — here's why
analysis

The "Phase-2 Cloud Sync (MySQL)" card in SettingsPage.tsx was originally designed for users to manually log into a separate cloud account and push/pull data. But the app is now already fully cloud-sync by default — every create/update/delete in BaseRepo goes to the cloud API automatically via canRemote().

The manual push/pull panel was a temporary workaround from an earlier architecture where the app was local-first with optional cloud. That design no longer exists — the app is cloud-first with local cache.

Recommendation: REMOVE it from user Settings

The cloud sync card:

  • Is already hidden (className="hidden")
  • Creates confusion — users shouldn't need to manually push/pull
  • Has a duplicate cloud login form that conflicts with the main CloudAuth
  • The underlying handleCloudPush/Pull functions can be kept as admin tools if needed

If you want a cloud sync indicator for users, replace it with a simple status badge in the header showing "Synced" / "Syncing..." / "Offline" — read-only, no manual action needed.

✅ Action: Delete the hidden card, add sync indicator to Header

In SettingsPage.tsx: delete the entire last <Card> block (Phase-2 Cloud Sync). In Header.tsx: add a small status dot (green = synced, yellow = pending, red = error) based on whether the last repo operation succeeded.
