1. Executive Summary

SparowVault is a thoughtfully architected, full-stack personal-finance platform. The frontend (React 19 + Vite + TypeScript with a Dexie/IndexedDB offline mirror) is well organized; the backend (PHP + MySQL with a custom router, custom JWT, bcrypt PIN hashing, and a Razorpay billing integration) shows clear discipline around the basics — prepared statements, constant-time HMAC compares, transactional payment updates, immutable admin audit logs, and a generic JSON entity store that lets new client features ship without schema migrations.

However, this audit is being delivered with an explicitly critical lens. The platform has several launch-blocking issues — most notably credentials and an example JWT secret shipped inside release/hosting-bundle/.env.host, the absence of HTTPS enforcement and baseline security headers (HSTS, CSP, X-Frame-Options), JWT tokens stored in localStorage (XSS-exfiltratable), and a Razorpay webhook handler that updates subscription state by provider_order_id alone without re-validating the owning user. There is also no self-service data-export or account-delete endpoint — a compliance gap under India's DPDP Act 2023 and GDPR.

None of these are architectural rewrites — they are hardening tasks measurable in days, not weeks. Once they're cleared the platform is in a defensible posture for a paid MVP.

3. Architecture & Module Design

3.1 High-level topology

SparowVault is a single-page React app served by Vite-built static assets, plus a stateless PHP API talking to MySQL. Each user has a server-side account (username + 4–8 digit PIN, bcrypt-hashed with a per-user salt) and a mirrored copy of all their data in browser IndexedDB via Dexie. The two stores are kept in sync via two endpoints: POST /api/cloud/sync/push.php and GET /api/cloud/sync/pull.php.

3.2 Frontend (React 19 + Vite + TypeScript)

Entry at src/main.tsx mounts ThemeProvider + AppProviders around the app shell. State is split across three Zustand stores (auth, data, navigation). The local DB schema in src/db/database.ts defines 21 Dexie stores: users, sessions, settings, accounts, cards, categories, transactions, budgets, loans, emiPayments, udhari, udhariSettlements, investments, savingsContributions, goals, goalContributions, reminders, alerts, recurringRules, attachments, auditLogs, snapshots, exportHistory — each carrying userId and an isDeleted flag with indexes tuned for the common queries (transactions by date / category / account).

The pages directory (src/components/pages/) covers Dashboard, Expenses, Income, Transactions, Accounts, Cards, Budgets, Goals, Loans, EMI, Investments, Udhari, Categories, Alerts, Audit, Reports, Subscription, Export/Import, Settings, Profile, plus admin pages for PlanManagement, UserManagement, SubscriptionManagement, FeatureFlags, BrandingSettings, AdminDashboard. Calculations are isolated in pure functions in src/services/calculations.ts, and alerts are derived in src/services/alertsEngine.ts.

The cloud client lives in src/lib/cloud/{auth,http}.ts — http.ts attaches the bearer JWT to every request and surfaces uniform errors; auth.ts implements register / login / me / change-pin. Crypto for local-only profiles is in src/lib/crypto.ts (Web Crypto API, SHA-256 with salt — courtesy hashing of PIN before it touches IndexedDB).

3.3 Backend (PHP + MySQL)

The entry router lives at php/index.php; the actual route table is in php/routes.php, a long sequence of conditional handlers mapping URIs to functions defined in php/controllers/* and helpers in php/helpers/*. Database access is centralized in php/config/db.php using PDO with prepared statements.

Endpoints split into four namespaces:

  • Auth (api/auth/*, api/cloud/*) — register, login, me, change-pin, reset-pin, profile, security-recovery, admin-login.
  • Sync & data (api/cloud/sync/*, api/cloud/entity*.php) — bulk push / pull and per-entity CRUD over the generic JSON store.
  • SaaS (api/subscriptions/*, api/payments/razorpay/*) — plans listing, order create, payment confirm, my-subscription, cancel, webhook handler.
  • Admin (api/admin/*) — plan / feature-flag / setting / user / subscription / audit administration, all role-gated.

3.4 Data model

The cleverest design decision in the codebase is cloud_collection_rows(user_id, collection_name, entity_id, payload LONGTEXT JSON, deleted_at, updated_at, …) with UNIQUE(user_id, collection_name, entity_id). All user-owned entities live here as JSON — no per-entity table, no migrations when the client adds fields. Soft-delete is via deleted_at.

On top of that sit dedicated SaaS tables: plans, plan_features, subscriptions, payments, webhook_events (idempotent via UNIQUE event_id), admin_audit_logs (immutable trail), login_attempts (brute-force tracking), api_rate_limits, app_settings, and feature_flags_global.

3.5 Trust boundaries

  • Browser → API: JWT (HS256) in Authorization: Bearer. Trust scope: one user.
  • API → MySQL: PDO with prepared statements; credentials from environment.
  • Razorpay → API: webhook signed with HMAC-SHA256 (RAZORPAY_WEBHOOK_SECRET); idempotent via webhook_events.event_id.
  • Admin → API: same JWT but role-gated. Role read from DB, not just claims.

4. End-to-End Flow Walkthroughs

4.1 New user sign-up & first sync

  1. User opens app → src/main.tsx mounts shell → useAuthStore.hydrate() finds no token → routes to Create-Account screen.
  2. Form posts to POST /api/cloud/register.php with { username, displayName, pin }.
  3. Server: validates regex (username 3–24 chars; PIN ^\d{4,8}$) → random_bytes(16) salt → password_hash(pin.":".salt, BCRYPT, cost=12) → INSERT into users → sign_cloud_token({userId,username,role:"user"}) with HS256, 7-day expiry.
  4. Response: { token, user }. Client stores token in localStorage (see Finding A8) and Zustand auth store.
  5. Client seeds local Dexie (default categories from defaultsService.ts) and immediately calls POST /api/cloud/sync/push.php to mirror the seed to cloud.

4.2 Adding an expense

  1. QuickAdd dialog writes a transaction object to the transactions Dexie store and updates Zustand.
  2. Dashboard re-derives KPIs by calling pure functions from src/services/calculations.ts — new monthly total, new budgetStatuses, new netMonthlySavings, refreshed healthScore.
  3. alertsEngine.ts runs idempotently: if Food budget passes 75% an in-app alert appears; if projected month-end exceeds budget a "projected overrun" alert is emitted.
  4. http.ts queues a push → sync/push.php upserts the row in cloud_collection_rows with collection_name='transactions'.

4.3 Subscribing to a paid plan (Razorpay)

  1. Frontend lists plans via GET /api/subscriptions/plans.php.
  2. User chooses plan → POST /api/subscriptions/create-order.php → server converts INR price to paise (×100), calls Razorpay Orders API with Basic-auth (key_id:key_secret), creates a pending subscription row, returns { order_id, amount, currency, key_id }.
  3. Frontend opens Razorpay Checkout with the order. User pays.
  4. Razorpay POSTs to /api/payments/razorpay/webhook.php with the event payload and the X-Razorpay-Signature header.
  5. Webhook handler:
    • Reads raw body.
    • Computes hash_hmac('sha256', body, RAZORPAY_WEBHOOK_SECRET).
    • Constant-time compares with hash_equals(). Good
    • Checks webhook_events.event_id uniqueness for idempotency.
    • On payment.captured: BEGIN TX → update payments → update subscriptions (status, period_start, period_end) → COMMIT.
Critical issue (F8): the subscription update in step 5 matches on WHERE provider_order_id = ? only — it does not verify the row's user_id against the user the order was originally created for. A crafted webhook with a real signature (or a confused-deputy scenario between staging/prod) could flip a different user's subscription. Add the user_id guard.

4.4 Admin actions

  1. Admin signs in via POST /api/auth/admin-login.php — same path as user login, plus role='admin' check.
  2. Each admin call goes through auth_require_admin() which re-reads role from the users table (not just the claim).
  3. Every state-changing action calls audit_log_action($actor, $action, $entityType, $entityId, $before, $after) writing into admin_audit_logs (immutable; no DELETE path in code).

5. Findings A — Security

A. Authentication & Session

A1CriticalProduction DB password shipped inside release bundle
D:\Claude\SparowVault\release\hosting-bundle\.env.host

The .env.host file previously shipped with concrete production credentials. If the bundle is ever uploaded to a folder served by Apache without an explicit deny, or pushed to a public artefact store, the password leaks.

Fix: Replace all sensitive values in .env.host with empty placeholders and comments; deliver real credentials via a password manager or deployment secret store. Add data/, .env, .env.host, .env.local to .gitignore; add explicit Apache <FilesMatch "\.(env|env\..*)$">Require all denied</FilesMatch> in .htaccess.
A2CriticalExample JWT secret embedded in release bundle
D:\Claude\SparowVault\release\hosting-bundle\.env.host (CLOUD_JWT_SECRET)

The packaged template includes a non-empty CLOUD_JWT_SECRET. Any deployment that does not actively overwrite it inherits a publicly-known signing key — every issued token becomes forgeable.

Fix: Make CLOUD_JWT_SECRET blank in the template and have php/config/env.php refuse to boot in APP_ENV=production when the secret is empty or matches a known-bad list. Generate per-deployment via openssl rand -hex 64.
A3HighJWT stored in localStorage on the client
D:\Claude\SparowVault\src\store\authStore.ts (token persist), D:\Claude\SparowVault\src\lib\cloud\http.ts (Authorization header)

Any reflected or stored XSS inside the app's origin can read the token and exfiltrate. The app pulls Razorpay's JS (third-party script) on the Subscription page — one supply-chain compromise of Razorpay's CDN is enough.

Fix: Move the token to an httpOnly; Secure; SameSite=Strict cookie set by the API on login. Add a CSRF defence — double-submit cookie or per-session CSRF token returned by /me and required on all non-GET requests.
A4HighCustom JWT implementation — small attack surface but no key rotation
D:\Claude\SparowVault\php\helpers\auth.php (sign_cloud_token / verify_cloud_token)

The hand-rolled HS256 implementation looks correct (base64url, hash_hmac('sha256', …, true), hash_equals for compare). There is no kid claim, so secret rotation forces every user to re-login. There is no alg allow-list against the classic "alg: none" attack — relying on the parser to reject it.

Fix: Explicitly check $header['alg'] === 'HS256' before verifying; reject anything else. Introduce a kid and a small map of active keys so rotation does not require global logout. Long-term, consider firebase/php-jwt or moving to RS256 for asymmetric verification.
A5HighNo JWT refresh; 7-day expiry stored client-side
D:\Claude\SparowVault\php\helpers\auth.php (CLOUD_JWT_EXPIRES_IN default 7d)

A long-lived bearer token in localStorage compounds A3 — once stolen it is good for up to a week.

Fix: Pair short access tokens (15–30 min) with a refresh token in an httpOnly cookie; rotate refresh on use; revoke on logout.
A6Confirmed GoodPIN hashed with bcrypt cost=12 over pin:salt
D:\Claude\SparowVault\php\helpers\auth.php (hash_secret / verify_secret)

random_bytes(16) generates the salt; password_hash(... PASSWORD_BCRYPT, ['cost'=>12]) hashes the concatenation. Verification uses password_verify. This is the correct pattern.

Keep: revisit cost annually as hardware speeds up.
A7Medium4-digit minimum PIN is weak in isolation
D:\Claude\SparowVault\php\controllers\cloud.php (regex ^\d{4,8}$)

10,000-key space; brute-force defence is wholly carried by login throttling. Acceptable for a banking-style PIN paired with throttling, but mark it as a known trade-off.

Fix: Bump minimum to 6 digits for new signups; add a "weak PIN" denylist (1234, 0000, 1111, etc.) and reject obvious sequences.
A8Confirmed GoodLogin throttling via DB with row-level UNIQUE constraint
D:\Claude\SparowVault\php\helpers\auth.php (login_throttle_status, record_login_failure)

Atomic INSERT … ON DUPLICATE KEY UPDATE on login_attempts with composite uniqueness on (username, ip_address). Lockout after a threshold. Cleared on success.

Keep. Add a sweeper (see A9).
A9MediumNo cleanup job for login_attempts or api_rate_limits

Both tables grow unbounded. Locked-out rows are never purged; rate-limit buckets accumulate dead keys.

Fix: Add a daily PHP cron / Webhook-triggered maintenance call that runs DELETE FROM login_attempts WHERE updated_at < NOW() - INTERVAL 7 DAY and DELETE FROM api_rate_limits WHERE window_start < NOW() - INTERVAL 1 DAY.
A10MediumRate-limit identity trusts X-Forwarded-For without validating proxy chain
D:\Claude\SparowVault\php\helpers\security.php (client_ip)

Behind an untrusted reverse proxy this is spoofable, defeating the per-IP limits in A8 and elsewhere.

Fix: Accept X-Forwarded-For / CF-Connecting-IP only when the immediate REMOTE_ADDR matches a configured trusted-proxy list (env: TRUSTED_PROXIES). Otherwise use REMOTE_ADDR.

B. Transport & Headers

A11HighNo HTTPS enforcement in .htaccess
D:\Claude\SparowVault\.htaccess

The SPA-fallback rules exist; there is no redirect of HTTP → HTTPS. On shared hosting that allows both, sessions can be initiated over plain TCP.

Fix:
RewriteEngine On
RewriteCond %{HTTPS} off
RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]
A12HighMissing security headers: HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy
D:\Claude\SparowVault\.htaccess

No Header set directives at all. A CSP in particular would meaningfully shrink the blast radius of the XSS-via-localStorage risk in A3.

Fix:
Header always set Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"
Header always set X-Frame-Options "DENY"
Header always set X-Content-Type-Options "nosniff"
Header always set Referrer-Policy "strict-origin-when-cross-origin"
Header always set Permissions-Policy "geolocation=(), microphone=(), camera=()"
Header always set Content-Security-Policy "default-src 'self'; script-src 'self' https://checkout.razorpay.com; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' https://api.razorpay.com; frame-src https://api.razorpay.com; base-uri 'self'; form-action 'self'"
A13HighNo deny rules for sql/, data/, php/, .env*
D:\Claude\SparowVault\.htaccess

If the hosting layout serves the project root, sql/*.sql and data/*.json are publicly fetchable. php/ is fine because PHP executes, but raw includes can be probed.

Fix:
<FilesMatch "(^\.env|\.env\..*|\.jwt-secret)$">Require all denied</FilesMatch>
<DirectoryMatch "(sql|data)">Require all denied</DirectoryMatch>
A14HighSource-map files shipped in the hosting bundle
D:\Claude\SparowVault\release\hosting-bundle\assets\*.js.map

Source maps leak the full TS source tree (route names, internal helpers, secrets accidentally inlined). Anyone fetching assets/index-*.js.map can reconstruct the codebase.

Fix: set build.sourcemap: false in vite.config.ts for prod, or post-build strip *.map from the bundle inside scripts/package-hosting.mjs.

C. CORS, CSRF, Input Validation

A15Confirmed GoodCORS uses exact-string allow-list, not wildcard, in production
D:\Claude\SparowVault\php\helpers\security.php

in_array($origin, $allowed, true) on a parsed CORS_ALLOWED_ORIGINS env var. Dev mode is more permissive — fine as long as APP_ENV=production is set.

Keep. Add a startup assertion that aborts in production when CORS_ALLOWED_ORIGINS is empty.
A16HighNo CSRF protection beyond CORS

Today, requests rely on the Authorization header being attached by JS. The moment the token moves to an httpOnly cookie (recommended in A3) CSRF becomes a real risk. Build the protection now to avoid forgetting later.

Fix: Issue a per-session CSRF token in a non-httpOnly cookie; require it as a header on POST/PATCH/DELETE; double-submit pattern. Pairs with the cookie-based JWT migration.
A17MediumNo server-side validation of cloud_collection_rows.payload shape
D:\Claude\SparowVault\api\cloud\sync\push.php (and entity.php)

Sync push stores client-supplied JSON verbatim. A malicious client can stuff in arbitrary fields, very large payloads, or unexpected types. The frontend trusts these on pull.

Fix: Validate each collection's payload with a JSON schema (zod or json-schema-validator-php) on push. Enforce a per-row size cap (suggest 64 KB; reject 1 MB+). Reject unknown collection_name values.
A18LowJWT secret file data/.jwt-secret
D:\Claude\SparowVault\data\.jwt-secret

If CLOUD_JWT_SECRET is unset the code falls back to a file in data/. On shared hosting filesystem perms can be looser than expected; if data/ is web-served (see A13), the secret is exposed.

Fix: require CLOUD_JWT_SECRET via env in production; emit a startup error if missing. Keep file fallback for local dev only.

D. Payments & Webhooks

A19Confirmed GoodRazorpay webhook signature verified with hash_equals
D:\Claude\SparowVault\php\helpers\payments.php

Constant-time compare of the HMAC. Raw body (not parsed JSON) is used as input — correct.

Keep.
A20Confirmed GoodWebhook idempotency via webhook_events.event_id UNIQUE
D:\Claude\SparowVault\sql\schema.sql (uq_webhook_event_id)

Replays are rejected at the DB level. Pair with the SQL-level transaction the handler already uses for the multi-table update.

A21CriticalWebhook updates subscription by order_id alone — missing ownership check
D:\Claude\SparowVault\api\payments\razorpay\webhook.php (subscription UPDATE)

The handler matches WHERE provider_order_id = ?. It does not verify that the row's user_id equals the user who initiated the order. A stolen order ID from logs, or a misconfigured staging webhook hitting prod, could update the wrong subscription.

Fix: On create-order.php record the (user_id, provider_order_id) tuple. In the webhook, UPDATE subscriptions ... WHERE provider_order_id = ? AND user_id = ?. Reject if zero rows touched. Log a security event if mismatch.
A22LowNo IP allow-list for Razorpay webhook endpoint

Defence in depth. The signature is the primary control; an IP allow-list of Razorpay's published egress prefixes adds a cheap second barrier.

Fix: Optional — gate /api/payments/razorpay/webhook.php by Razorpay's documented IPs in .htaccess or PHP-level.
A23MediumRazorpay webhook does not validate signed_payload.amount against the stored order amount

An attacker who can present a valid signature for a small captured payment could potentially flip a subscription whose stored order was much larger, if the handler trusts only the event type.

Fix: Re-fetch the order via Razorpay's API (or compare against the local payments.amount_inr stored at order creation) before activating the subscription. Reject mismatched amounts.

E. Admin & Authorization

A24Confirmed GoodAdmin role re-read from DB, not just from JWT claim
D:\Claude\SparowVault\php\helpers\auth.php (auth_require_admin)

Resists privilege-elevation via stolen old tokens whose claim is stale.

A25MediumNo IP / UA logging in user-facing audit trail

admin_audit_logs captures IP + UA. There is no equivalent for user-side state changes (transactions, subscription cancel).

Fix: Add a thinner user_audit_logs table or extend the existing one to user actions, even if only for billing-relevant events at first.
A26LowPassword / PIN never logged (good)
D:\Claude\SparowVault\php\helpers\observability.php (request_log)

request_log() does not deep-copy and scrub the body. Today no one logs the request body, but if a future engineer adds error_log(json_encode($_POST)) the PIN ends up in PHP error logs.

F. Frontend Surface

A27MediumExternal script (Razorpay Checkout) loaded without SRI

The Razorpay checkout script is fetched from their CDN. Subresource Integrity is not feasible since Razorpay rotates the script, but pin the script to a single trusted origin via the CSP (A12) and avoid loading any other third-party JS.

A28LowNo clickjacking protection beyond X-Frame-Options

After A12 is applied (X-Frame-Options + CSP frame-ancestors 'none') this is closed.

There is no service worker; pure Dexie offline. Not a defect, but if a PWA is added later, treat the SW cache as a privileged origin.

This is fine for the local-only profile case it was designed for; it is not a defence against device compromise and should not be portrayed as such in UI copy.

6. Findings B — Business Logic & Calculations

6.1 EMI / Amortization

B1Confirmed GoodEMI handles 0% interest and tenure=0 edge cases
D:\Claude\SparowVault\src\services\calculations.ts (calculateEMI)

Code does if (!principal || !tenureMonths) return 0 and if (monthlyRate === 0) return principal / tenureMonths — both correct.

B2MediumAmortization final-payment rounding can leave a residual balance

EMI is rounded for display; the schedule subtracts min(balance, EMI − interest) each month. With float math you can end up at the last row with a tiny non-zero balance (e.g., ₹0.04). Reports look wrong.

Fix: On the last scheduled month, force the principal portion to equal the remaining balance and adjust that month's EMI display accordingly. Better: do all money math in paise integers.
B3HighAll money stored in rupees as floats — rounding risk

Across the schema and the JSON payloads, amounts are decimals. JS floats lose precision at 0.1 + 0.2. For a finance product, this is a slow bleed of trust.

Fix: Convert internal storage and computations to paise as BIGINT / number integers, format to rupees only at the view edge. This is a multi-day refactor; budget for it.

6.2 Budgets, Projections & Savings

B4Confirmed GoodProjected month-end spend uses correct day denominator

avgPerDay = spentSoFar / daysElapsed, projected = avgPerDay × daysInMonth. Day counts use date-fns differenceInCalendarDays(today, startOfMonth)+1 — handles the first-of-month edge cleanly.

B5LowProjection is naive linear — ignores weekday seasonality and pending recurring expenses

For an MVP this is acceptable. Worth a callout because the "Projected to overrun" alert can fire spuriously early in the month.

Fix (v2): Subtract known recurring debits already scheduled before extrapolating; or compute a 7-day rolling average.
B6MediumSavings rate clamps to ±999% — silently masks bugs

Useful for display but if a category-misclassification bug makes income negative, the user sees "Savings rate −100%" not an error.

Fix: Emit a debug-level alert when clamping happens; surface a "Check your data" hint in the dashboard.
B7MediumHealth-score weights are undocumented magic numbers

Weights such as 22 / 14 / 14 / 14 / 12 / 14 / 10 sum to 100 by design but the rationale is invisible to a future maintainer.

Fix: Pull weights into a single typed constants object with a doc comment justifying each. Test that weights sum to 100 in a unit test.

6.3 Goals & Recurring

B8Confirmed GoodGoal monthly-required formula handles past-due target dates

monthlyRequired = monthsLeft > 0 ? remaining / monthsLeft : remaining — collapses to "pay it all now" instead of dividing by zero.

B9MediumRecurring-rule materialization can duplicate when client time skews

If the rule says "every 1st of month" and the user opens the app at 23:59 IST on the 1st in two different time-zones, two transactions can be created.

Fix: Each recurring rule should write a deterministic occurrenceKey = ruleId + 'YYYY-MM' and the entity insert should be idempotent on that key.

6.4 Subscription Period Math

B10HighNew period starts from NOW() even when user renews before expiry
D:\Claude\SparowVault\api\payments\razorpay\webhook.php (subscription period update)

A user who renews on day 25 of a 30-day plan loses 5 paid days. Fair? No. Customer-support nightmare.

Fix: new_period_start = MAX(NOW(), current_period_end). Extend from end-of-current.
B11MediumNo proration on plan upgrade / downgrade

Switching plans mid-cycle simply rewrites the row. No credit applied.

Fix: For MVP, allow upgrade only at period boundary; document it in UI. Add proration in v1.

6.5 Currency, Timezone, Locale

B12LowAll calculations assume INR + IST without an explicit setting

Fine for India-only MVP; document the assumption in src/constants/index.ts.

B13MediumCross-account transfer has no fromAccount != toAccount guard

A self-transfer would zero-net but pollute the transaction list.

Fix: Validate in the form and on push.php.
B14LowNegative amount inputs not rejected server-side

Frontend usually prevents this; server should also.

Fix: Validate amount > 0 in push.php for transaction-shaped payloads.

7. Findings C — Code Quality

8. Findings D — Database

D1Confirmed GoodForeign keys with ON DELETE CASCADE across user-owned tables

F1HighNo self-service data-export endpoint (DPDP / GDPR)

India's DPDP Act 2023 (and GDPR Article 20 for EU users) requires users be able to download their data in a machine-readable form.

F2HighNo self-service account deletion (DPDP / GDPR)

Likewise, the right to erasure. Cascade FKs are in place; expose the action.

F4MediumNo privacy policy / ToS surfaced in product

Soft-deleted rows linger indefinitely.

12.3 Core formulas, restated

EMI = P × r × (1 + r)^n / ((1 + r)^n − 1)
       where r = annualRate / 12 / 100, n = tenureMonths
       0%-interest fallback: EMI = P / n

Amortization, per month k:
       interest_k  = balance_{k-1} × r
       principal_k = min(balance_{k-1}, EMI − interest_k)
       balance_k   = balance_{k-1} − principal_k

Net monthly savings = income − expense − EMI − CC payments − udhari given
Savings rate (%)    = clamp(netSavings / income × 100, −100, 999)
Projected spend     = (spentSoFar / daysElapsed) × daysInMonth
Budget % used       = spent / budgeted × 100

Goal monthly required = remaining / max(1, monthsLeft)
Goal on-track if pacePerMonth ≥ monthlyRequired × 0.9
