# SparowVault API and Data Audit - 11 September 2026

Companion to [the current full audit](FULL-PROJECT-AUDIT-2026-09-11.md). This replaces earlier API pass/fail assumptions for the current working tree, not the historical evidence itself. Sources were read from `api/`, `php/controllers/`, `php/helpers/`, the collection contracts and the browser client. No production server was attacked or changed.

## Reading the Evidence

- There are **41 PHP endpoint files**, not 41 independent services. Several are aliases for the same controller; a file can accept several methods.
- `extended-final-verified/audit/api-matrix.json` records direct HTTP checks. The isolated integrity and statement suites additionally exercise writes, batch/sync rollback, sessions, imports and financial side effects.
- The 37 collection-list tests each check authenticated owner, another requested owner and anonymous access. Passing a list probe does **not** certify every field, CRUD method or relationship in that collection.
- Nine admin endpoints were called as anonymous and ordinary users: all 18 calls denied access but returned **500**, not the intended **401/403**. This is an error-contract defect, not a demonstrated admin authorization bypass.
- Six admin GET routes returned success for the synthetic administrator. Destructive admin UI operations were not all executed.
- Route wrappers commonly return caught exception text with a 500 response. Centralize typed public errors and log private detail server-side. The statement endpoint already returns a sanitized temporary-failure response.

Evidence base: [extended audit](audit-evidence/2026-09-11-full/extended-final-verified/atomic-writes.json), [baseline verification](audit-evidence/2026-09-11-full/verification/verification.json), [full collection/field catalog](FULL-AUDIT-CATALOG-2026-09-11.md).

## Shared Contracts

Authentication is server-validated user identity and session state, not a trusted request `userId`. Browser sessions use an HTTP-only cookie with a CSRF token for mutations; the API harness also exercises owner-bound bearer sessions. Ordinary writes need a valid session and CSRF for cookie authentication, not a fresh PIN on every operation. PIN replacement, security recovery and privacy export have additional credential checks.

The common envelope is `ok` plus `data` or `error`; request IDs and machine-readable error codes are available in shared helpers. Expected statuses include 200/201 success, 400 malformed input, 401 no valid credentials, 403 forbidden/CSRF/feature restrictions, 404 missing row, 409 mutation/version/reference conflict, 422 invalid domain input and 429 throttling. Do not interpret a 500 denial as a successful role bypass. Invalid JSON and unsupported collection names are rejected in fresh probes.

Collection endpoints use query keys `collection` and, for item operations, `id`. Creates use an owner-bound `userId`, `data` and an optional mutation key. Batch/sync shapes are controller-specific. Tests must read the current request contracts rather than reuse obsolete fixtures. Versioned mutations and payload-bound receipt replay work; an omitted expected version still permits stale overwrites.

## Database and Ownership

The backend uses SQL, not the Vercel Blob JSON store assumed by the agency brief. `cloud_collection_rows` stores owner/collection/entity-keyed JSON with query/index fields. SQL tables separately store user/session, subscription/payment, webhook, mutation receipt, audit and ledger/event/effect state. IndexedDB is a browser cache and durable outbox, not the sole authoritative finance database. Zustand holds the active view.

All 37 collection contracts, their aliases, required/optional fields, indexed fields and declared migration rules are reproduced in the [catalog](FULL-AUDIT-CATALOG-2026-09-11.md). The names `emis`, `savingsContribs` and `goalContribs` differ from some TypeScript/Dexie names. Restore/sync code must use the mapping intentionally, not derive names heuristically.

### Verified Write Guarantees

- Twenty-four concurrent equal-key/equal-payload retries create one receipt/row; different payloads cannot reuse that key.
- Server owner locks and SQL transactions cover entity, ledger effects, immutable receipt and server audit writes on the tested finance path.
- A failed batch or sync rolls back earlier writes. The final reference graph is checked independently of collection order.
- Soft/hard deletes cannot be resurrected by a stale snapshot; ledger effects are invalidated while a server audit record remains.
- Existing and foreign transaction parent references are checked. Attempting to delete an account still referenced by a transaction is blocked.
- A persisted browser outbox survives a real browser restart and two-tab reconnect. A rejected item can be downloaded and resolved against the server version.

### Confirmed Gaps

1. **Version optionality:** older clients can omit an expected version and overwrite a newer edit. Require versions on updates/deletes and make any legacy migration explicit and non-destructive.
2. **Schema asymmetry:** accounts and loans with invalid domain values persist with 201. Contract metadata is not a server validator. Add collection-specific validation before any ledger/receipt/source commit.
3. **Relationship asymmetry:** orphan goal contributions and EMI rows persist with 201. Validate every parent under the same owner and transaction boundary; add delete/reassignment rules.
4. **Visible audit mutability:** the user can create and delete rows in the client `auditLogs` collection. The separate server audit is retained, but the UI is not an authoritative tamper-evident view.
5. **Domain-operation boundaries:** goal contribution and Udhari settlement are multi-repository operations in the UI. Happy-path saves pass; induced failure between each step and concurrent settlement caps are not fully verified. Move complete domain operations behind transactional endpoints before relying on them for company books.
6. **Migration confidence:** fresh-schema integration and a genuine backup restore pass. That is not evidence that every historical SQL script safely upgrades an existing database. Old gate names such as "certify" and "dry run" are not guarantees.

## Security Follow-Ups Before Production

Do not copy XAMPP root/no-password database access or local HTTP settings into deployment. Provision a least-privilege SQL account, maintained database/runtime, managed secrets, TLS and a trusted-proxy boundary. Verify Apache actually applies security headers and access-denial rules; PHP's development server does not evaluate `.htaccess`. Test HMAC retry behavior against the official [Razorpay validation guidance](https://razorpay.com/docs/webhooks/validate-test/), including invalid signatures, valid retries, out-of-order events and temporary processing failure. An event should be deduplicated as complete only after authenticated processing commits.

No broad claim of GDPR/DPDP, tax, PCI or penetration-test certification is made. Those require deployment, operational and legal evidence beyond source comments and local tests.
